# Known limits and documented boundaries

AgentExperience.NET is a **preview**. It is not production ready, and it does not claim to be. This page is the
honest list of what stands between it and a production-readiness claim, and of what it can never do.

- **Known limits** are problems a code change could fix. While this table has a row, the version must stay a
  preview.
- **Documented boundaries** are properties no code change can remove. They are stated exactly here, and they do not
  block a release: a production-readiness claim would be made with them stated.

A preview may drop its suffix only when the Known limits table is empty **and** every item on the maintainers'
deferred-work ledger is closed. [`RELEASING.md`](../RELEASING.md) step 9 counts this file's Known limits rows, and
the tag-triggered release workflow runs the same count; the ledger is not in the repository, so no command can check
it, and the maintainer who drops the suffix confirms it is closed. It is not closed today, so this version stays a
preview. The rationale for splitting the two tables is recorded in
[`RELEASING.md`](../RELEASING.md#decision-known-limits-and-documented-boundaries).

The release gate reads this file, and the GitHub release notes quote both tables, which is why the table links are
absolute. Keep the two `##` headings below and the shape of each table: a known limit is a three-cell row
(`| KL-n | limit | where the detail lives |`), and a documented boundary is a five-cell row.

What was resolved or narrowed in earlier previews, and how, is in [Limits history](limits-history.md).

## Known limits

Every unresolved limit this release knows about that a code change could fix, one row each, with where the detail
lives. **A row leaves this table only by fixing the limit.** The one other way out is for a row to turn out not to be
a limit at all: it may move to [Documented boundaries](#documented-boundaries) only with a written reason why no code
change can remove it, and it returns here if that reason stops holding.

**None currently.**

## Documented boundaries

Properties the library cannot remove by code, because they are inherent to PostgreSQL, to what independence can
prove, or to how models work. Each row states the boundary exactly, why no code change can remove it, and what the
library does about it. They are not softened by being here. A row arrives here from [Known limits](#known-limits)
only with its written reason, keeps its number, and returns to that table if the reason stops holding.

| KL-2 | **Erasure cannot reach a copy of the derived search data, and without crypto-shredding it reaches only live rows.** With `ExperienceEncryption` configured (opt-in), erasing a record destroys its key, so its text is unreadable in every backup, replica, WAL segment and dead tuple — except its full-text vector (the task ID, summary and lesson as lexemes with positions) and its embedding vector, which PostgreSQL has to read in the clear and which survive in every copy exactly as plaintext does (the embedding's content hash is stored keyed under the record's key, so once the key is destroyed it no longer confirms a guessed summary, although two copies still show whether the summary changed between them, story 17.5). Never sealed, in either mode: IDs, scope, statuses, scores, timestamps, principal identities, and a grant's argument allowlist (tool names and argument keys). Rows written before a deployment switched modes keep their plaintext copies (and append-only ledger rows stay plaintext until erased). In plaintext mode, still the default, every copy keeps everything and the dead tuple keeps the text until `VACUUM`. Exported telemetry, server logs and external artifacts are out of reach, and the property is only as good as a key store kept outside the database's backups | PostgreSQL has to read the full-text vector and the embedding in the clear to search and rank on them, and has to read IDs, scope, statuses, scores and timestamps in the clear to filter, authorize and order; sealing them would remove the search, not the copy. Backups, replicas, WAL, exported telemetry, server logs and external artifacts are made and kept outside the library's reach, so it cannot delete from them; the only thing it can destroy is a key, and a key store is custody the host provides. Crypto-shredding needs that key store, so it cannot be the default, and a copy made before a deployment switched modes was made before there was a key to destroy | Opt-in crypto-shredding (`ExperienceEncryption` over an `IExperienceKeyStore`) seals every free-text column erasure removes under a per-record key held outside the database and destroys the key inside the erasure's transaction; the embedding's content hash, which search does not need, is stored as an HMAC under a subkey of the same key rather than in the clear, so no copy can confirm a guessed summary once the key is gone (a hash written in the clear for a record that has a key costs one re-embed); `SealPlaintextRecordsAsync` seals existing records; the envelope key store supports KEK rotation; and the guides state exactly what erasure does and does not reach | [Crypto-shredding](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/crypto-shredding.md); [What deletion does not reach](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/deletion-and-retention.md#what-deletion-does-not-reach-in-plaintext-mode) |
| KL-11 | **Verified independence proves a run was *given* the lesson, not that it used it; the library still believes the host's own bookkeeping and key custody; and the opt-out's evidence counts unless the host keeps it out.** By default confidence evidence and attributed feedback must name a run the library knows in the record's scope (finalized there by the library, or held by the capture service), never the record's own, whose provenance shows the library delivered the record into it at or before the revision the evidence is computed against; a machine round must be the one finalization closed, and a human assessment must present a single-use HMAC token. What remains: (1) *delivered* is not *used*, so every run that was given a lesson is one key, whether or not the lesson mattered to it; (2) the library believes the host's own bookkeeping and key custody where it cannot see past them — a host that calls `IExperienceCaptureService.RecordExposure` for records it did not deliver is believed; without provenance signing (opt-in, `ExperienceProvenanceSigningOptions`), so is a host that writes a record through `CreateAsync` marked `ExperienceRecordOrigin.Finalized` (and an application role while it holds `AllowSealing`, which can replace a plaintext payload), while with signing on a record written or edited outside finalization cannot pass as finalized (an edit to its content is caught only for a record signed with claims version 2, story 17.2; a version 1 signature covers the finalization claims alone), but whoever holds a signing key can sign any claims and content, and the records a host lists in the signing cutover (`TrustUnsignedRecordIds`, captured once from the records that existed when signing was switched on) are believed unsigned; the round finalization records is the `ClosedRound` the host passed it (evidence carries no run ID, so no check can tie a round, or a direct `VerificationAggregator.Aggregate` caller's run ID, to the run itself; a direct aggregator result counts only through finalization or such a marked record), and whoever holds `AssessmentTokenKey`, or can call `AssessmentTokenIssuer`, can mint a valid token; (3) a host that opts out with `IndependenceVerification.TrustHostSuppliedIdentifiers` still has every `RunId`, `VerificationRoundId` and `AssessmentId` trusted, and one that lets agent output populate them hands the agent a fresh key per call — that evidence is stored as `HostTrusted`, tagged in telemetry, and left out on request by `ReadConfidenceAsync`, and under the default `HostTrustedEvidenceEffect.Counted` it moves the stored score retrieval ranks on, the counters and, for a contradiction, the status; with `ExperienceIndependenceOptions.HostTrustedEvidence = RecordedOnly` it moves none of them (story 17.3), but evidence counted before that was set stays counted | Whether a model *used* what it was given is not observable from outside the model, so no check can tell delivered from used. The library runs inside the host's process and on the host's database role: whatever the host calls, writes or holds (exposures, a record marked `Finalized`, `AllowSealing`, the `ClosedRound`, the assessment token key, the provenance signing keys) is the host's own statement, and nothing below the host can check it against the run itself. The opt-out exists for a host that cannot adopt verification, and trusting its identifiers is what opting out means; whether that trusted evidence also moves the ranked score is the host's setting (`Counted` stays the default, so an upgrade changes no score). Evidence already counted stays counted because counters move only through append-only lifecycle events: taking it back out would mean appending events that reverse evidence the record accepted, and the read that leaves it out (`ExcludeHostTrusted`) already exists | Verification is on by default: evidence must name a run the library knows in the record's scope that was exposed to the record at or before the evidence's revision, a machine round must be the one finalization closed, and a human assessment must present a single-use, expiring HMAC token. With provenance signing configured, finalization signs each record's finalization claims (HMAC-SHA256 under a host-held key ring) and a run whose record is unsigned, signed under an unknown key, or changed after signing vouches for nothing. Under the opt-out, only a finalized record whose signature is present, under a known key, and invalid is refused. Opted-out evidence is stored as `HostTrusted`, tagged in telemetry, and excluded on request by `ReadConfidenceAsync`; with `HostTrustedEvidence = RecordedOnly` (after migration `0023` in PostgreSQL, without which every host-trusted submission fails) it is recorded on its event without moving the record's counters, score, status or `UpdatedAt`, so it steers neither ranking nor eligibility; the event still advances the revision and history as a counted one does, and `ReadConfidenceAsync` with `All` adds it back with the counts and score the default would have stored (not its status or de-indexing) | [Confidence and independence](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/confidence.md); [Keeping host-trusted evidence out of the ranked score](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/confidence.md#keeping-host-trusted-evidence-out-of-the-ranked-score); [Signing provenance](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/confidence.md#signing-provenance); [Reuse feedback](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/reuse-feedback.md); [Verifying a run](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/finalization.md#verifying-a-run-and-binding-its-evaluation) |
| KL-12 | **A withdrawn record's text stays in a reused session, and the withdrawal is advisory.** Session tracking (on by default) bounds what a session is given, never repeats a revision (while a concurrent invocation's delivery is pending, only within `InFlightStageWindow` and the eight-stage bound), and tells the model when a record it was given is no longer valid (erased, revoked, superseded, quarantined, contested, un-granted, below the confidence floor or past `MaxAge`) — but the earlier block stays in the history, verbatim, and a model that read it cannot be made to forget it. The provider cannot strip its own earlier blocks, and the tracking is only as trustworthy as the host's session storage: removing or replacing the state key resets it or substitutes another account, and two processes that resume the same serialized session each keep their own copy of it, so they can deliver the same revision twice and the copy saved last wins. A host that turns tracking off (`SessionLimits = null`) is back to unbounded accumulation with no notices | A model's context is the conversation history, which the host owns, and a model that has read a block cannot be made to unread it; no code in a context provider can edit an earlier turn or a model's memory of it. The tracking has to live in the host's session storage, the only state that travels with the session, so it is exactly as durable as that storage is, and a lock inside one process cannot serialize another process's copy of the session: that needs a lock in the host's storage, which the library does not own. Turning tracking off is the host's choice for a chat history that already drops injected blocks | Session tracking is on by default: a session gets a bounded budget, never the same revision twice, and one fixed withdrawal notice, carrying no reason and no content, for each record it holds that is no longer valid. Within one process, invocations on one session are serialized by a per-session lock held from reading the account to writing it back (never across the model call), and each in-flight invocation's delivery is staged on its own and counted as delivered until that invocation settles it or `InFlightStageWindow` (default 5 minutes) passes, after which it is committed as unsure, as an abandoned stream's is; so concurrent invocations within the window neither repeat a revision nor lose a charge or a delivery (story 17.4). The injected block is labelled as reference, and the control that matters, the approval boundary around tools, lives outside the block | [Injection into MAF](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/injection.md); [Reused sessions](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/injection.md#reused-sessions-a-budget-no-repeats-and-withdrawal-notices) |
| KL-17 | **Row-level security confines a mistake in the stores' SQL, not the application role, and it is not a complete second copy of every rule.** With `ExperienceApplicationRoleOptions.EnableRowLevelSecurity` on (opt-in, story 15.1), every covered table admits the application role only inside the authorization bounds the current store operation declared for its transaction, and the owner's erasure, purge and sealing functions refuse a scope outside them. But those bounds are settings any session may set, so a host that runs arbitrary SQL as the application role can declare any tenant's bounds and act inside them as the stores' own predicates allow. The policies do not enforce a grant's disclosure level (redaction is in the library's code); a caller-chosen record ID that collides with another tenant's still reveals that it exists elsewhere (`Conflict` on create); the record a reuse feedback exposure names is not checked; and text search under the policies uses the table-wide GIN index, so its cost reflects matches in every tenant (a weak timing and statistics side channel) | PostgreSQL has no setting a role can be kept from setting for its own session, and a policy can only compare a row with what the session declared; binding the database to the caller's identity instead needs a database role per tenant or principal, a different deployment. Caller-chosen record IDs are globally unique by design, so a colliding ID reports `Conflict`: an accepted design trade, since making them unique per scope would rekey every table, and finalization's own derived IDs mix in the scope, so they cannot collide across tenants. An exposure of an unknown record is kept as `Unresolved` by design, so feedback for a record erased since it was injected still records, and checking a record's existence under row-level security would itself reveal that it exists. Disclosure is a projection of a row, not a row. A GIN index that leads with the tenant needs the `btree_gin` extension, which the library does not require, and the table-wide index is what keeps a large tenant's search off a scan | The policies are a superset of every store predicate and never replace one, admit nothing when nothing is declared, never admit a write through a grant, and are never forced. The privileges call re-creates them from their canonical definitions and verifies them, and refuses to enable them over a missing or extra policy, a preset default for their settings, an unreadable grant table, or an application role that can reach `BYPASSRLS`. Text search keeps its GIN index under the policies through `search_experience_text` (`0024`, story 17.7), an owner-run function that applies the read policy's own admission through the same helpers, which the privileges call grants only while row-level security is on (there is no opt-out: enabling requires it) and checks when it enables row-level security, refusing one altered by hand; a `CREATE OR REPLACE` the owner runs afterwards is used until the next privileges call | [Enabling row-level security](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/deployment.md#enabling-row-level-security) |
