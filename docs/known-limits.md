# Known limits and documented boundaries

AgentExperience.NET is a **preview**. It is not production ready, and it does not claim to be. This page is the
honest list of what stands between it and a production-readiness claim, and of what it can never do.

- **Known limits** are problems a code change could fix. While this table has a row, the version must stay a
  preview.
- **Documented boundaries** are properties no code change can remove. They are stated exactly here, and they do not
  block a release: a production-readiness claim would be made with them stated.

A preview may drop its suffix only when the Known limits table is empty **and** every item on the maintainers'
deferred-work ledger is closed. [`RELEASING.md`](../RELEASING.md) step 9 counts this file's Known limits rows, and
the tag-triggered release workflow runs the same count; the ledger is not in the repository, so no command can check
it, and the maintainer who drops the suffix confirms it is closed. It is not closed today, so this version stays a
preview. The rationale for splitting the two tables is recorded in
[`RELEASING.md`](../RELEASING.md#decision-known-limits-and-documented-boundaries).

The release gate reads this file, and the GitHub release notes quote both tables, which is why the table links are
absolute. Keep the two `##` headings below and the shape of each table: a known limit is a three-cell row
(`| KL-n | limit | where the detail lives |`), and a documented boundary is a five-cell row.

What was resolved or narrowed in earlier previews, and how, is in [Limits history](limits-history.md).

## Known limits

Every unresolved limit this release knows about that a code change could fix, one row each, with where the detail
lives. **A row leaves this table only by fixing the limit.** The one other way out is for a row to turn out not to be
a limit at all: it may move to [Documented boundaries](#documented-boundaries) only with a written reason why no code
change can remove it, and it returns here if that reason stops holding.

**None currently.**

## Documented boundaries

Properties the library cannot remove by code, because they are inherent to PostgreSQL, to what independence can
prove, or to how models work. Each row states the boundary exactly, why no code change can remove it, and what the
library does about it. They are not softened by being here. A row arrives here from [Known limits](#known-limits)
only with its written reason, keeps its number, and returns to that table if the reason stops holding.

| KL-2 | **Erasure cannot reach a copy of the derived search data, and without crypto-shredding it reaches only live rows.** With `ExperienceEncryption` configured (opt-in), erasing a record destroys its key, so its text is unreadable in every backup, replica, WAL segment and dead tuple — except its full-text vector (the task ID, summary and lesson as lexemes with positions) and its embedding with its content hash, which PostgreSQL has to read in the clear and which survive in every copy exactly as plaintext does. Never sealed, in either mode: IDs, scope, statuses, scores, timestamps, principal identities, and a grant's argument allowlist (tool names and argument keys). Rows written before a deployment switched modes keep their plaintext copies (and append-only ledger rows stay plaintext until erased). In plaintext mode, still the default, every copy keeps everything and the dead tuple keeps the text until `VACUUM`. Exported telemetry, server logs and external artifacts are out of reach, and the property is only as good as a key store kept outside the database's backups | PostgreSQL has to read the full-text vector and the embedding in the clear to search and rank on them, and has to read IDs, scope, statuses, scores and timestamps in the clear to filter, authorize and order; sealing them would remove the search, not the copy. Backups, replicas, WAL, exported telemetry, server logs and external artifacts are made and kept outside the library's reach, so it cannot delete from them; the only thing it can destroy is a key, and a key store is custody the host provides. Crypto-shredding needs that key store, so it cannot be the default, and a copy made before a deployment switched modes was made before there was a key to destroy | Opt-in crypto-shredding (`ExperienceEncryption` over an `IExperienceKeyStore`) seals every free-text column erasure removes under a per-record key held outside the database and destroys the key inside the erasure's transaction; `SealPlaintextRecordsAsync` seals existing records; the envelope key store supports KEK rotation; and the guides state exactly what erasure does and does not reach | [Crypto-shredding](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/crypto-shredding.md); [What deletion does not reach](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/deletion-and-retention.md#what-deletion-does-not-reach-in-plaintext-mode) |
| KL-11 | **Verified independence proves a run was *given* the lesson, not that it used it; the library still believes the host's own bookkeeping and key custody; and the opt-out's evidence is excluded only on read.** By default confidence evidence and attributed feedback must name a run the library knows in the record's scope (finalized there by the library, or held by the capture service), never the record's own, whose provenance shows the library delivered the record into it at or before the revision the evidence is computed against; a machine round must be the one finalization closed, and a human assessment must present a single-use HMAC token. What remains: (1) *delivered* is not *used*, so every run that was given a lesson is one key, whether or not the lesson mattered to it; (2) the library believes the host's own bookkeeping and key custody where it cannot see past them — a host that calls `IExperienceCaptureService.RecordExposure` for records it did not deliver is believed; without provenance signing (opt-in, `ExperienceProvenanceSigningOptions`), so is a host that writes a record through `CreateAsync` marked `ExperienceRecordOrigin.Finalized` (and an application role while it holds `AllowSealing`, which can replace a plaintext payload), while with signing on a record written or edited outside finalization cannot pass as finalized, but whoever holds a signing key can sign any claims, and the records a host lists in the signing cutover (`TrustUnsignedRecordIds`, captured once from the records that existed when signing was switched on) are believed unsigned; the round finalization records is the `ClosedRound` the host passed it (evidence carries no run ID, so no check can tie a round, or a direct `VerificationAggregator.Aggregate` caller's run ID, to the run itself; a direct aggregator result counts only through finalization or such a marked record), and whoever holds `AssessmentTokenKey`, or can call `AssessmentTokenIssuer`, can mint a valid token; (3) a host that opts out with `IndependenceVerification.TrustHostSuppliedIdentifiers` still has every `RunId`, `VerificationRoundId` and `AssessmentId` trusted, and one that lets agent output populate them hands the agent a fresh key per call — that evidence is now stored as `HostTrusted`, tagged in telemetry, and left out on request by `ReadConfidenceAsync`, but the stored score retrieval ranks on still counts it | Whether a model *used* what it was given is not observable from outside the model, so no check can tell delivered from used. The library runs inside the host's process and on the host's database role: whatever the host calls, writes or holds (exposures, a record marked `Finalized`, `AllowSealing`, the `ClosedRound`, the assessment token key, the provenance signing keys) is the host's own statement, and nothing below the host can check it against the run itself. The opt-out exists for a host that cannot adopt verification, and trusting its identifiers, in the score it asked to be computed, is what opting out means | Verification is on by default: evidence must name a run the library knows in the record's scope that was exposed to the record at or before the evidence's revision, a machine round must be the one finalization closed, and a human assessment must present a single-use, expiring HMAC token. With provenance signing configured, finalization signs each record's finalization claims (HMAC-SHA256 under a host-held key ring) and a run whose record is unsigned, signed under an unknown key, or changed after signing vouches for nothing. Under the opt-out, only a finalized record whose signature is present, under a known key, and invalid is refused. Opted-out evidence is stored as `HostTrusted`, tagged in telemetry, and excluded on request by `ReadConfidenceAsync` | [Confidence and independence](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/confidence.md); [Signing provenance](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/confidence.md#signing-provenance); [Reuse feedback](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/reuse-feedback.md); [Verifying a run](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/finalization.md#verifying-a-run-and-binding-its-evaluation) |
| KL-12 | **A withdrawn record's text stays in a reused session, and the withdrawal is advisory.** Session tracking (on by default) bounds what a session is given, never repeats a revision, and tells the model when a record it was given is no longer valid (erased, revoked, superseded, quarantined, contested, un-granted, below the confidence floor or past `MaxAge`) — but the earlier block stays in the history, verbatim, and a model that read it cannot be made to forget it. The provider cannot strip its own earlier blocks, and the tracking is only as trustworthy as the host's session storage: removing the state key resets it, and concurrent invocations on one session race on it. A host that turns tracking off (`SessionLimits = null`) is back to unbounded accumulation with no notices | A model's context is the conversation history, which the host owns, and a model that has read a block cannot be made to unread it; no code in a context provider can edit an earlier turn or a model's memory of it. The tracking has to live in the host's session storage, the only state that travels with the session, so it is exactly as durable and as serialized as that storage is. Turning tracking off is the host's choice for a chat history that already drops injected blocks | Session tracking is on by default: a session gets a bounded budget, never the same revision twice, and one fixed withdrawal notice, carrying no reason and no content, for each record it holds that is no longer valid. The injected block is labelled as reference, and the control that matters, the approval boundary around tools, lives outside the block | [Injection into MAF](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/injection.md); [Reused sessions](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/injection.md#reused-sessions-a-budget-no-repeats-and-withdrawal-notices) |
| KL-17 | **Row-level security confines a mistake in the stores' SQL, not the application role, and it is not a complete second copy of every rule.** With `ExperienceApplicationRoleOptions.EnableRowLevelSecurity` on (opt-in, story 15.1), every covered table admits the application role only inside the authorization bounds the current store operation declared for its transaction, and the owner's erasure, purge and sealing functions refuse a scope outside them. But those bounds are settings any session may set, so a host that runs arbitrary SQL as the application role can declare any tenant's bounds and act inside them as the stores' own predicates allow. The policies do not enforce a grant's disclosure level (redaction is in the library's code); unique indexes span tenants, so a colliding ID still reveals that it exists elsewhere (`Conflict` on create); the record a reuse feedback exposure names is not checked; and full-text search cannot use its GIN index beneath the policies, so it scans the declared tenant's live records | PostgreSQL has no setting a role can be kept from setting for its own session, and a policy can only compare a row with what the session declared; binding the database to the caller's identity instead needs a database role per tenant or principal, a different deployment. A policy sees a row outside the bounds exactly as it sees no row, so it cannot tell an exposure of a foreign record from one of an unknown record the port allows. Disclosure is a projection of a row, not a row. `@@` is not leakproof, and marking a built-in function leakproof is a superuser's call | The policies are a superset of every store predicate and never replace one, admit nothing when nothing is declared, never admit a write through a grant, and are never forced. The privileges call re-creates them from their canonical definitions and verifies them, and refuses to enable them over a missing or extra policy, a preset default for their settings, an unreadable grant table, or an application role that can reach `BYPASSRLS`. The scope index bounds a text search to one tenant | [Enabling row-level security](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/deployment.md#enabling-row-level-security) |
| KL-18 | **A model-authored lesson is marked by its reflector, filtered by a heuristic, and neither its text nor its authorship is signed.** Story 14.3 marks a reflection's `Authorship`, filters model-authored text with a fixed content guard (credential shapes, mixed-script words, listed instruction-override phrasing, and URLs, hostnames and IP addresses the run did not show the reflector), and labels or excludes model-authored records at injection. What remains: authorship is self-declared, so a third-party model-backed reflector that does not set `Model` is treated as deterministic (the library's own `ChatClientExperienceReflector` is recognised by its producer, so its records count as model-authored whatever they declare; it shipped in `0.1.0-preview.5`, the release that also made it declare `Model`, so no database a published release wrote holds one of its records flagged otherwise); the guard passes content echoed from the run, a poisoned tool result included, paraphrased or translated instructions, whitespace-split dots, encoded secrets and mid-line contradictions, and it can refuse a legitimate lesson; and provenance signing covers the finalization claims only, so a party that can write the store can change a reflection's text or authorship | Whether text steers a model is a property of the model, not of the text: no fixed filter recognizes every instruction, and a model call to judge it would be steerable in turn. A reflector is a host seam, so only it knows whether a model wrote its output; the library can vouch only for its own reflector's producer, and inferring authorship from another producer's text would be a guess a reflector could defeat by naming itself differently. Signing the free text would not stop the reflector's own model from writing a steered lesson | The guard is applied to every model-authored reflection and refuses, never truncates; injection labels every model-written field between two fixed lines and fails closed on any authorship other than `Deterministic`; `ModelAuthoredLessons = Exclude` omits such records before the record limit, and a PostgreSQL search fails closed on a row whose authorship flag is unknown until the owner-run `BackfillSealedAuthorshipAsync` writes it; the approval boundary around tools stays the control for anything a lesson induces | [Limits of model-authored lessons](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/finalization.md#limits-of-model-authored-lessons); [Model-authored lessons](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/injection.md#model-authored-lessons); [Backfilling authorship flags](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/crypto-shredding.md#backfilling-authorship-flags-after-upgrading) |
