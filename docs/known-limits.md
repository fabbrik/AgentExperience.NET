# Known limits and documented boundaries

AgentExperience.NET is a **preview**. It is not production ready, and it does not claim to be. This page is the
honest list of what stands between it and a production-readiness claim, and of what it can never do.

- **Known limits** are problems a code change could fix. While this table has a row, the version must stay a
  preview.
- **Documented boundaries** are properties no code change can remove. They are stated exactly here, and they do not
  block a release: a production-readiness claim would be made with them stated.

A preview may drop its suffix only when the Known limits table is empty **and** every item on the maintainers'
deferred-work ledger is closed. [`RELEASING.md`](../RELEASING.md) step 9 counts this file's Known limits rows, and
the tag-triggered release workflow runs the same count; the ledger is not in the repository, so no command can check
it, and the maintainer who drops the suffix confirms it is closed. It is not closed today, so this version stays a
preview. The rationale for splitting the two tables is recorded in
[`RELEASING.md`](../RELEASING.md#decision-known-limits-and-documented-boundaries).

The release gate reads this file, and the GitHub release notes quote both tables, which is why the table links are
absolute. Keep the two `##` headings below and the shape of each table: a known limit is a three-cell row
(`| KL-n | limit | where the detail lives |`), and a documented boundary is a five-cell row.

What was resolved or narrowed in earlier previews, and how, is in [Limits history](limits-history.md).

## Known limits

Every unresolved limit this release knows about that a code change could fix, one row each, with where the detail
lives. **A row leaves this table only by fixing the limit.** The one other way out is for a row to turn out not to be
a limit at all: it may move to [Documented boundaries](#documented-boundaries) only with a written reason why no code
change can remove it, and it returns here if that reason stops holding.

**None currently.**

## Documented boundaries

Properties the library cannot remove by code, because they are inherent to PostgreSQL, to what independence can
prove, or to how models work. Each row states the boundary exactly, why no code change can remove it, and what the
library does about it. They are not softened by being here. A row arrives here from [Known limits](#known-limits)
only with its written reason, keeps its number, and returns to that table if the reason stops holding.

| # | Boundary | Why no code change can remove it | What the library does about it | Where the detail lives |
| --- | --- | --- | --- | --- |
| KL-2 | **Erasure cannot reach a copy of the derived search data, and without crypto-shredding it reaches only live rows.** With `ExperienceEncryption` configured (opt-in), erasing a record destroys its key, so its text is unreadable in every backup, replica, WAL segment and dead tuple — except its full-text vector (the task ID, summary and lesson as lexemes with positions) and its embedding with its content hash, which PostgreSQL has to read in the clear and which survive in every copy exactly as plaintext does. Never sealed, in either mode: IDs, scope, statuses, scores, timestamps, principal identities, and a grant's argument allowlist (tool names and argument keys). Rows written before a deployment switched modes keep their plaintext copies (and append-only ledger rows stay plaintext until erased). In plaintext mode, still the default, every copy keeps everything and the dead tuple keeps the text until `VACUUM`. Exported telemetry, server logs and external artifacts are out of reach, and the property is only as good as a key store kept outside the database's backups | PostgreSQL has to read the full-text vector and the embedding in the clear to search and rank on them, and has to read IDs, scope, statuses, scores and timestamps in the clear to filter, authorize and order; sealing them would remove the search, not the copy. Backups, replicas, WAL, exported telemetry, server logs and external artifacts are made and kept outside the library's reach, so it cannot delete from them; the only thing it can destroy is a key, and a key store is custody the host provides. Crypto-shredding needs that key store, so it cannot be the default, and a copy made before a deployment switched modes was made before there was a key to destroy | Opt-in crypto-shredding (`ExperienceEncryption` over an `IExperienceKeyStore`) seals every free-text column erasure removes under a per-record key held outside the database and destroys the key inside the erasure's transaction; `SealPlaintextRecordsAsync` seals existing records; the envelope key store supports KEK rotation; and the guides state exactly what erasure does and does not reach | [Crypto-shredding](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/crypto-shredding.md); [What deletion does not reach](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/deletion-and-retention.md#what-deletion-does-not-reach-in-plaintext-mode) |
| KL-11 | **Verified independence proves a run was *given* the lesson, not that it used it; the library still believes the host's own bookkeeping and key custody; and the opt-out's evidence is excluded only on read.** By default confidence evidence and attributed feedback must name a run the library knows in the record's scope (finalized there by the library, or held by the capture service), never the record's own, whose provenance shows the library delivered the record into it at or before the revision the evidence is computed against; a machine round must be the one finalization closed, and a human assessment must present a single-use HMAC token. What remains: (1) *delivered* is not *used*, so every run that was given a lesson is one key, whether or not the lesson mattered to it; (2) the library believes the host's own bookkeeping where it cannot see past it — a host that calls `IExperienceCaptureService.RecordExposure` for records it did not deliver, or writes a record through `CreateAsync` marked `ExperienceRecordOrigin.Finalized`, is believed (so is an application role while it holds `AllowSealing`, which can replace a plaintext payload), and the round finalization records is the `ClosedRound` the host passed it (evidence carries no run ID, so no check can tie a round, or a direct `VerificationAggregator.Aggregate` caller's run ID, to the run itself; a direct aggregator result counts only through finalization or such a marked record), and whoever holds `AssessmentTokenKey`, or can call `AssessmentTokenIssuer`, can mint a valid token; (3) a host that opts out with `IndependenceVerification.TrustHostSuppliedIdentifiers` still has every `RunId`, `VerificationRoundId` and `AssessmentId` trusted, and one that lets agent output populate them hands the agent a fresh key per call — that evidence is now stored as `HostTrusted`, tagged in telemetry, and left out on request by `ReadConfidenceAsync`, but the stored score retrieval ranks on still counts it | Whether a model *used* what it was given is not observable from outside the model, so no check can tell delivered from used. The library runs inside the host's process and on the host's database role: whatever the host calls, writes or holds (exposures, a record marked `Finalized`, `AllowSealing`, the `ClosedRound`, the assessment token key) is the host's own statement, and nothing below the host can check it against the run itself. The opt-out exists for a host that cannot adopt verification, and trusting its identifiers, in the score it asked to be computed, is what opting out means | Verification is on by default: evidence must name a run the library knows in the record's scope that was exposed to the record at or before the evidence's revision, a machine round must be the one finalization closed, and a human assessment must present a single-use, expiring HMAC token. Opted-out evidence is stored as `HostTrusted`, tagged in telemetry, and excluded on request by `ReadConfidenceAsync` | [Confidence and independence](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/confidence.md); [Reuse feedback](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/reuse-feedback.md); [Verifying a run](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/finalization.md#verifying-a-run-and-binding-its-evaluation) |
| KL-12 | **A withdrawn record's text stays in a reused session, and the withdrawal is advisory.** Session tracking (on by default) bounds what a session is given, never repeats a revision, and tells the model when a record it was given is no longer valid (erased, revoked, superseded, quarantined, contested, un-granted, below the confidence floor or past `MaxAge`) — but the earlier block stays in the history, verbatim, and a model that read it cannot be made to forget it. The provider cannot strip its own earlier blocks, and the tracking is only as trustworthy as the host's session storage: removing the state key resets it, and concurrent invocations on one session race on it. A host that turns tracking off (`SessionLimits = null`) is back to unbounded accumulation with no notices | A model's context is the conversation history, which the host owns, and a model that has read a block cannot be made to unread it; no code in a context provider can edit an earlier turn or a model's memory of it. The tracking has to live in the host's session storage, the only state that travels with the session, so it is exactly as durable and as serialized as that storage is. Turning tracking off is the host's choice for a chat history that already drops injected blocks | Session tracking is on by default: a session gets a bounded budget, never the same revision twice, and one fixed withdrawal notice, carrying no reason and no content, for each record it holds that is no longer valid. The injected block is labelled as reference, and the control that matters, the approval boundary around tools, lives outside the block | [Injection into MAF](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/injection.md); [Reused sessions](https://github.com/fabbrik/AgentExperience.NET/blob/main/docs/guide/injection.md#reused-sessions-a-budget-no-repeats-and-withdrawal-notices) |
